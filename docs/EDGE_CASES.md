# Edge cases

Real edge cases in Esports Pakistan's actual code — not generic "what if the network fails" advice. Each entry names the scenario, what should happen, and what the code actually does today (file/function referenced). Where a gap is real and unaddressed, it says so plainly instead of implying it's handled. Companion to [`ARCHITECTURE.md`](ARCHITECTURE.md) (why the system is shaped this way) and [`SECURITY.md`](SECURITY.md) (which of these were found and fixed as part of a security/business-logic audit, with regression tests).

## Purpose

This file documents real, project-specific edge cases — concurrency races, state-machine gaps, production incidents, and known limitations actually found in this codebase — not generic "what if X fails" advice that would apply to any project. It exists so a gap that's already been found and fixed once (or deliberately left as a known tradeoff) doesn't get silently rediscovered, re-debated, or re-broken later.

## Status legend

Every entry ends with one of these:

- **Handled** — currently protected by the code, working as intended.
- **Fixed** — a real bug was found and fixed (regression-tested where applicable); the entry describes what the bug *was*, not a live issue.
- **Needs improvement** — a known, currently-open gap. See the `Priority` label on each of these for how urgent it actually is.
- **Known limitation / Understood** — an intentional tradeoff or a real constraint that's deliberately not being reactively patched — scoped as future architectural work, not an oversight.

## Registration & email-OTP verification

**Two people register the same email before either verifies.** `RegisterSerializer.create()` (`core/serializers.py`) uses `PendingRegistration.objects.update_or_create(email=...)` — the second signup silently overwrites the first's `PendingRegistration` row (new password hash, new OTP). *Handled*: this is deliberate, not a bug — see the docstring at the call site. It means "I typo'd my password, let me sign up again" just works instead of erroring; the tradeoff is the first attempt's OTP silently stops working with no notice to whoever is holding it. Since no `User` exists yet either way, there's no account-takeover risk — worst case is a confused second signup attempt.

**OTP guessed wrong 5 times.** `core/otp.py:verify_otp` locks the code out permanently (`otp_attempts >= OTP_MAX_ATTEMPTS`) — the *correct* code stops working too, not just further wrong guesses. *Handled*: by design, this forces a fresh `resend-verification` call rather than allowing unlimited retries against one leaked/guessed code. The 60-second resend cooldown (`can_resend()`) means an attacker can't immediately reset their own attempt budget by spamming resend either.

**Resending a code while the previous one is still unexpired.** `issue_otp()` unconditionally overwrites `otp_hash`/`otp_expires_at`/`otp_attempts` on resend. *Handled*: the old code stops working the instant a new one is issued (no dual-valid-codes window) — correct, since a resend implies "the last one didn't arrive," not "I want two valid codes."

**Verifying with a completely unknown email.** `VerifyEmailView` returns the identical `{'otp': 'Invalid or expired code.'}` shape whether the `PendingRegistration` doesn't exist at all, is expired, or is locked — deliberately, so brute-forcing the endpoint can't distinguish "no such pending signup" from "wrong code," which would otherwise leak which email addresses have an in-progress signup. *Handled*, tested (`core/tests.py:VerifyEmailApiTests.test_verify_unknown_email_rejected`).

**Registering as an organizer, then never verifying.** The uploaded CNIC/company documents (already pushed to Cloudinary at registration time, per `RegisterSerializer`) sit referenced only by the `PendingRegistration` row. *Fixed*: nothing pruned orphaned Cloudinary uploads or stale `PendingRegistration` rows for abandoned signups before — they'd accumulate indefinitely (a storage-growth concern, not a security one). `core/management/commands/cleanup_pending_registrations.py` now deletes rows older than `--older-than-days` (default 7, well past the OTP's own 10-minute expiry — this is about abandonment, not the OTP window itself), deleting each row's Cloudinary-hosted `cnic_document`/`company_document` first if present. A Cloudinary delete failure for one row is logged and skipped, not allowed to block the rest of the cleanup run — same "one bad item doesn't break the batch" principle used for announcement emails. Not wired to run automatically (no Celery/task queue in this codebase) — same as `flushexpiredtokens`, it's meant to be invoked by an external scheduler (a Render Cron Job); see `SECURITY_CHECKLIST.md`'s "Scheduled cleanup" section. Regression tests: `core/tests.py:CleanupPendingRegistrationsCommandTests`.

**The registration email itself fails to send (Brevo down, bad API key).** `RegisterView.create()` (`core/views.py`) still returns `201` with a "we couldn't send the code, use resend" message rather than turning a real signup into a 500 over an unrelated email outage. *Handled* — this is the exact reasoning documented inline: retrying registration would just refresh the same pending row with no way to know the first attempt "failed" for an unrelated reason.

## Google OAuth

**Same Google-verified email as an existing password account.** `GoogleLoginView`'s `User.objects.get_or_create(email=...)` silently links the two — the password account gains `google_id` and becomes sign-in-with-Google-capable too. *Handled, intentional*: matched only on Google's own verified `email` claim, never anything client-asserted, so this can't be triggered by an attacker claiming someone else's email — see `SECURITY.md#authentication`.

**A captured `(state, id_token)` pair replayed after a successful login.** `cache.set(f'google_oauth_state_used:{state}', ...)` marks it single-use only *after* a successful login — a replay attempt against the same pair gets rejected. *Handled*, tested (`core/tests.py:GoogleLoginApiTests.test_google_login_state_cannot_be_replayed_after_a_successful_login`). Note the asymmetry: a failed attempt (bad token, Google unreachable) does *not* mark the state used, so a legitimate retry after a transient failure isn't blocked by the replay guard — only genuine successes consume it.

**Google is unreachable mid-login (network blip, Google outage).** Split deliberately from "your token is bad": a `GoogleAuthError` reaching Google's cert-verification servers becomes a distinct `503 GoogleAuthUnavailable`, not the same `400` a malformed/expired token gets. *Handled* — the frontend can tell "try again shortly" apart from "something is wrong with your Google session" this way, though the current frontend chatbot-style error handling for this specific path hasn't been audited for whether it actually surfaces that distinction to the user (see the RAG chatbot's own generic-error-swallowing pattern below, which is the same class of frontend issue in a different feature).

**A `state` value crafted by an attacker and pushed onto a victim's browser (login CSRF).** *Known, unresolved limitation, documented rather than silently left implicit*: `state` isn't bound to the browser tab/session that requested it. Someone who completes their own legitimate Google login could get their own valid `(state, id_token)` processed on a victim's browser via a crafted page — forcing the victim to end up authenticated as the *attacker's* account, not an account takeover of the victim's own account. See `SECURITY.md#authentication`'s "Known residual limitation" — the real fix (authorization-code+PKCE) is a deliberate future migration, not something patched reactively.

**Google's `id_token` says `email_verified: false`.** Rejected outright (`GoogleLoginView`) rather than trusted for linking/creating an account — an email Google itself hasn't confirmed the user controls shouldn't be trusted to attach to (or create) an account. *Handled*, tested.

## Tournament lifecycle

**Cancelling a tournament that already has registrations or a bracket.** `lifecycle.cancel_tournament` raises `NeedsAdminReview` instead of executing — the organizer's own request becomes an `AdminReviewRequest`, not a silent no-op or a 500. *Handled* — see the admin-review escalation pattern in `ARCHITECTURE.md`. The safety check (`_is_safe_to_self_cancel`) lives *inside* the service function, not the view, so a future third caller (bulk-admin action, management command) gets the same protection automatically without remembering to reimplement it — verified directly by `tourny_regist/tests.py:ServiceLayerInvariantTests`, which calls the function with no view in between.

**Double-clicking "cancel" (or a retried request) while the first request is still being reviewed.** All three escalation call sites (`TournamentCancelView`/`RegistrationCancelView`/`TournamentBracketResetView`) used to create a fresh `AdminReviewRequest` on every retry. *Fixed*: `AdminReviewRequest.Meta` has a partial `UniqueConstraint` (one `pending` request per target+type); each view catches the resulting `IntegrityError` and still returns its normal `202`, so a retry is a clean no-op instead of an admin queue full of duplicates.

**Rescheduling doesn't introduce a `POSTPONED` status.** `reschedule_tournament` updates `starts_at`/`ends_at`/`registration_deadline` in place and logs the *old* values into `AuditLog.metadata` rather than adding a new lifecycle state. *Handled, deliberate* — this is an audited edit, not a distinct status, per the function's own docstring. A tournament rescheduled five times has five audit entries, not five statuses to reason about elsewhere in the codebase.

**Duplicating a tournament copies configuration, not participants.** `duplicate_tournament` explicitly copies only `COPIED_ON_DUPLICATE` fields (game, format, venue, contacts, ...) — never registrations, teams, brackets, matches, champion state, or the compliance documents. The new tournament starts as a fresh `DRAFT`; documents are re-required at `submit_tournament` time. *Handled, deliberate* — a duplicate is "run this again," not "clone this event with its participants."

**Raising `team_size` on a tournament that already has a team registered at the old size.** *A real gap, found and fixed*: raising `team_size` after registration used to reopen a team's roster capacity — a team registered at exactly the old cap could suddenly accept a new member the organizer never agreed to when they submitted the roster. `TournamentUpdateSerializer` now freezes `game`/`team_size`/`bracket_format` once *any* registration, team, or bracket exists. Resending the *same* value (the frontend always resends the whole form) is fine — only an actual change is blocked. See `SECURITY.md`'s business-logic section.

**Two Swiss-round-advance requests firing back to back.** `generate_next_swiss_round` refuses to advance until every match in the current round is `COMPLETED` — a second concurrent call sees the same "round not finished" state and correctly rejects rather than generating a duplicate round. Not lock-mediated in the same sense as bracket-generation's tournament lock, since the guard is a plain status check rather than a race between two *simultaneous* generations of the same round — worth confirming this stays true if a future change makes Swiss round-generation itself do more than validate-then-create.

## Registration & team concurrency

**Two registrations landing on the last open slot at the same instant.** *A real gap, found and fixed*: `RegistrationCreateView` used to check `tournament.registrations.count() >= max_participants` with no lock — two simultaneous requests could both read "under the cap" and both succeed, overselling the tournament. Fixed by `select_for_update()` on the `Tournament` row for the whole check-then-create sequence, mirroring `TeamJoinView`'s existing pattern for the same race on team-roster slots. Regression test uses real threads against a real database (`tourny_regist/tests.py:RegistrationCapacityConcurrencyTests`), not a single-transaction simulation that can't actually exercise the race.

**The same player registering twice for one tournament.** Backstopped independently of any lock: `Registration.Meta`'s `UniqueConstraint(fields=['tournament', 'player'])` — even if a locking bug were ever introduced elsewhere, the database itself refuses the duplicate row.

**A player creating team A and joining team B at the same instant.** *A second real gap, found in a follow-up audit*: `TeamCreateView`/`TeamJoinView` each locked only the team row they directly touched — a brand-new team has no row to lock yet, so neither request serialized against the other, and each one's "am I already on a team for this tournament?" check ran before the other's membership committed. Fixed by having both lock the *Tournament* row instead (the shared resource between the two different paths to the same outcome), not the team each path happens to create/touch. Regression test: `TeamMembershipConcurrencyTests` (real threads).

**Hard-deleting your own registration after a bracket exists.** *A real gap, found and fixed*: `RegistrationDeleteView` (a player's own self-withdrawal) had no state check at all — a player could delete their registration after being seeded into a live match (even after *winning* one), orphaning the opponent's match with no forfeit recorded, then immediately re-register with a clean row — evading the admin-review gate `cancel_registration` enforces for exactly this case. Fixed: blocked entirely, for the player and for staff via the same endpoint, once `hasattr(tournament, 'bracket')` — withdrawal past that point must go through `disqualify_registration`, which knows how to unwind a live match (auto-forfeits any match the player is currently `READY` to play).

**Checking in (or un-checking-in) after a bracket has already been generated.** *A real gap with two parts, found and fixed*: (1) the terminal-status blocklist only covered `REJECTED`, so a `DISQUALIFIED`/`CANCELLED` registration with `registration_fee == 0` (the default) could be checked back in as if the disqualification never happened; (2) there was no bracket-existence check at all — `standings()`/`generate_next_swiss_round()` re-derive the eligible pool *live* from whoever is currently `checked_in`, not a roster frozen at bracket-generation time, so a late check-in injects a fresh player into a later round, and an un-check-in silently drops someone with a completed, won match with no forfeit. Fixed: check-in status is frozen both directions once a bracket exists; removing a bracket-era participant must go through `disqualify_registration` instead.

**Reinstating a disqualified or cancelled registration via the ordinary review endpoint.** *A real gap, found and fixed*: `RegistrationReviewSerializer` (organizer approve/reject of a registration) had no valid-transition whitelist at all, unlike its `AdminTournamentUpdateSerializer` sibling — a plain `PATCH {"status": "approved"}` could silently reinstate a disqualified/cancelled registration, undoing a forfeit's implications without undoing the forfeit itself, no reason required. Fixed: `DISQUALIFIED`/`CANCELLED` are now terminal from this endpoint. (Reviewing an already-`APPROVED` registration back to `REJECTED` or vice versa is still allowed on purpose — e.g. discovering a fraudulent payment proof after initially approving it.)

**Substituting a team member after matches have already been played.** `substitute_team_member` only swaps the *roster* (`TeamMembership`) — it deliberately never touches `Match.player1`/`player2`, which already point at the specific `User` who actually played. *Handled* — a substitution can't retroactively rewrite who competed in a completed match; it only affects who's eligible to play from that point forward, and only on an already-`is_locked` team (staff-only, an "exceptional workflow" distinct from ordinary pre-lock roster changes).

## Bracket engine

**A field size that isn't a power of two.** `_seed_slots`/`_next_power_of_two` pad the field with byes up to the next power of two for single elimination, and `_build_losers_bracket` builds the losers bracket from the *actual* winners-bracket topology round by round (not the classic fixed seed-round/drop-in formula, which only works for a clean power of two) — so double elimination and the 3-game guarantee format also handle a non-power-of-two field correctly via the same general mechanism, not just single elimination. *Handled* — verified directly in `brackets/services.py`, contrary to what might be assumed from the format's minimum-count checks alone (double elim needs ≥4 checked-in players, guarantee3 needs ≥8 — those are participation floors, not a power-of-two requirement).

**A round-1 bye immediately advancing a player with no result submitted.** `_build_single_elim` auto-completes every round-1 bye match the instant the bracket is generated — by construction, standard seeding (`_seed_order`) never pairs two byes against each other, so exactly one of "player1 present, no player2" / "player2 present, no player1" applies per bye match. *Handled.*

**Telling a real "only one player was ever going to be here" bye apart from "one slot just hasn't been filled in yet by an earlier match."** `_is_bye_match` checks whether a slot is fed by an upstream match (`_fed_slots`), not just whether it's currently empty — a naive `bool(player1_id) != bool(player2_id)` check would misclassify a round-2 match (one slot already arrived via a completed round-1 bye, the other slot's feeder match hasn't been played yet) as a bye, understating how many real games its eventual participants will have played. This specifically matters for the 3-game-guarantee format's accounting. *Handled* — documented explicitly as the reason this isn't a simpler check.

**Two simultaneous match-result submissions for the same bracket.** Enforced by a strict lock order (Tournament → Bracket → Match) that makes deadlock impossible *by construction*, not by hoping two code paths never disagree — `complete_match` takes the tournament lock first specifically because the "obvious" implementation (lock the match, then the tournament once a result is decided) inverts against bracket generation's own lock order (tournament, then any newly-created bye matches). `LockOrderAuditTests` statically parses `services.py`'s AST and fails the suite if a new `select_for_update()` shows up that isn't accounted for in the ordering — so this survives refactoring, not just a one-time review. *Handled*, with the explicit cost documented: result submissions for one tournament serialize on its row (acceptable — low-frequency, short transactions).

**Bracket routing tries to overwrite an already-occupied match slot.** `_advance_into` refuses to displace a different player already standing in a slot — a malformed graph routing two different sources into the same destination would otherwise silently evict someone from a match they'd earned, and the bracket would still *look* plausible afterward. *Handled* — fails loudly (`ValidationError`) rather than corrupting state quietly; re-writing the *same* player into a slot is allowed, so a safe retry is possible.

**Two players tied on every configured tiebreaker.** `standings()` always falls back to registration order as the final tiebreak — two players equal on wins and every named tiebreaker still rank in a stable, deterministic order rather than an arbitrary one that could change between requests. *Handled.*

**A Swiss round that would pair a lone survivor against nobody.** `_build_losers_bracket`'s merge/pair loop (shared machinery, also relevant to double-elim/guarantee3's losers bracket) creates no `Match` rows and doesn't consume a round number when a pairing step would produce zero real matches — no phantom empty rounds appear in the bracket. *Handled.*

**Overriding a match result, or forfeiting a bye.** `override_match_result` explicitly rejects overriding a bye's result (`'A bye has no result to override.'`) and rejects re-recording the same winner that's already recorded. `forfeit_match` rejects forfeiting against a bye (`'A bye has no opponent to forfeit against.'`). *Handled* — both are real, reachable inputs (an admin fat-fingering the wrong match), not defensive dead code.

## Admin review & disputes

**Attaching more "evidence" to, or escalating, a dispute that's already been resolved.** *A real gap, found and fixed*: `DisputeEvidenceUploadView`/`DisputeEscalateView` had no status check at all, unlike their sibling `DisputeStatusView`, which already refused further action once `RESOLVED`/`DISMISSED`. A stakeholder could keep acting on a dispute whose decision was already final. Fixed to match.

**A non-stakeholder guessing a dispute ID.** Returns `404`, not `403` — deliberately, so a wrong guess doesn't even confirm the dispute exists. *Handled.*

**An admin granting/revoking `is_staff` with only a stolen-but-valid access token.** `AdminUserDetailView.update` requires the acting admin's *own current password* in the request body for this specific change, re-checked via `request.user.check_password` — not just "does this bearer token currently work." *Handled* — this doesn't require a *recent* login, just proof the caller still knows the password right now; a stolen token alone (XSS, an unattended browser) isn't enough to mint or deactivate an admin account.

**An admin accidentally removing their own `is_staff`/`is_active` via the same endpoint.** Blocked outright by `AdminUserDetailView` — a guard against an admin locking themselves out of the admin surface entirely (or being tricked into it via a crafted request). *Handled.*

**A staff account approving/rejecting a review request that's already been decided.** `AdminReviewRequestDecideView` locks the `AdminReviewRequest` row for the check-then-decide sequence — a second concurrent decide attempt on the same (already-committed) request sees its updated status and correctly rejects rather than double-processing it. *Handled.*

**An organizer re-uploading CNIC/company documents after already being approved.** `OrganizerUploadCnicView`/`OrganizerUploadCompanyView` didn't check the organizer's current `status` before accepting a new document — an already-`APPROVED` organizer could silently swap their CNIC or company registration document without triggering any re-review. *Fixed*: `_reopen_review_after_document_change()` (`organizer/views.py`) now sends the application back to `PENDING` whenever a document is (re-)uploaded while `APPROVED` — the same admin review a fresh application gets, logged via `core.audit.log_action('organizer.compliance_document_replaced', ...)`. The existing `last_seen_status`/`OrganizerAcknowledgeStatusView` mechanism (already built for surfacing an approval/rejection to the organizer) picks this up automatically, with no new frontend notification path needed. Deliberately still a no-op for `PENDING` (already awaiting a first review) and `REJECTED` (re-uploading before calling the separate resubmit endpoint is the existing, intentional flow — see `OrganizerResubmitView`'s docstring) — only `APPROVED → PENDING` is a real re-review event. Regression tests: `organizer/tests.py:test_upload_cnic_after_approval_reopens_review`/`test_upload_company_document_after_approval_reopens_review`/`test_upload_cnic_while_pending_does_not_touch_status`/`test_upload_cnic_while_rejected_does_not_auto_resubmit`.

**Reinstating a previously-rejected organizer application.** `AdminOrganizerUpdateSerializer` intentionally allows re-deciding an already-rejected application directly (no `PENDING`-only restriction, unlike its `AdminTournamentUpdateSerializer` counterpart) — confirmed deliberate by `organizer/tests.py:test_approve_clears_previous_rejection_reason`, which exercises exactly this. *Handled, and specifically flagged in `SECURITY.md` as a near-miss*: an earlier attempt to "fix" this asymmetry for consistency with the tournament-approval pattern would have broken this intentional behavior — worth re-checking existing tests before assuming two similar-looking serializers should behave identically.

## Email (Brevo)

**Brevo rejects a send because the sender address isn't verified in that account.** Surfaces as a `RuntimeError` from `BrevoAPIBackend` — still not raised back to the end user for the announcement/reschedule email paths, which deliberately keep swallowing per-recipient failures so one bad send doesn't 500 an entire announcement post; that part is unchanged, intentional design. *Fixed* (visibility only, not the swallow-per-recipient behavior): `_send_one` used to fold the status code and Brevo's response body into a generic `logger.exception` traceback — diagnosable, but only by reading a full stack trace line by line. It now logs a distinct, clearly-labeled line *before* raising (`'Brevo API rejected an email to %s (subject=%r): HTTP %s — %s'`), and a separately-labeled line for the different failure mode of Brevo being unreachable at all (network/DNS/timeout, `requests.exceptions.RequestException`) rather than actively rejecting the request — the two used to look identical in the logs, and are actually different problems (one is "fix your Brevo config," the other is "wait and retry"). Still requires actually testing a real send end-to-end (trigger one, check Brevo's dashboard Email Activity) rather than assuming it works because the key is set — logging can't detect a failure that never happens to occur during testing. Regression tests: `core/tests.py:BrevoAPIBackendTests.test_rejected_send_logs_status_code_and_response_body`/`test_unreachable_api_raises_and_is_logged_distinctly_from_a_rejection`.

**A message with an attachment reaches `BrevoAPIBackend`.** Every current call site sends plain-text, no attachments — `BrevoAPIBackend` doesn't implement Brevo's attachment format at all. If one ever is attempted, it logs a loud warning (not a silent drop) rather than pretending to send it. *Handled defensively* — correctly scoped to what's actually used today, with a clear signal if that scope is ever exceeded without extending the backend deliberately.

**`BREVO_API_KEY` unset in production.** `config/settings.py` raises `ImproperlyConfigured` at *settings-load* time when `ENVIRONMENT=production` — the app refuses to boot rather than silently falling back to the console backend (which would print password-reset links and verification codes to stdout in production logs). *Handled*, but with a documented diagnostic wrinkle: if this fires during `entrypoint.sh`'s `migrate --noinput` step, Django's management-command bootstrapping partially swallows the real exception and surfaces a confusing, unrelated-looking `DATABASES is improperly configured` error instead. The deploy still correctly fails either way — **this is not hypothetical**: it's exactly what happened in this project's own production deploy history (see the Infrastructure section below), and cost real debugging time before the actual cause (a missing env var, not a database problem) was identified via the raw WSGI boot path instead of the migrate-step traceback.

## RAG chatbot

**A question about a game with no rulebook uploaded.** The prompt (`groq_service.py`) explicitly instructs the model to say `GUARDRAIL_MESSAGE` ("I can only answer questions related to esports rules and the uploaded documents.") rather than hallucinate an answer when the retrieved context doesn't address the question — and if `retrieve_candidates` finds nothing relevant (because no chunks with that `game_name` exist at all), there's genuinely nothing grounded to answer from. *Handled correctly* — verified directly during this project's own rulebook rollout: a corpus with only one game's rulebook uploaded made every other game's questions correctly decline rather than fabricate an answer. This is expected, desired behavior, not a bug, and shouldn't be "fixed" by loosening the grounding instruction.

**A follow-up question that doesn't name a game.** `retrieve_candidates`'s `fallback_game` parameter carries the *previous conversation turn's* detected game forward (`ChatHistory.game_name`), so "what about substitutes?" right after a Tekken 8 answer stays scoped to Tekken 8 instead of searching unscoped across every uploaded game. *Handled* for the common case.

**A single question names two different games at once.** *A real gap, found and fixed*: "compare Tekken 8 and PUBG's substitution rules" used to silently collapse to whichever single game `game_detector.detect_game()` ranked highest (most regex hits, ties broken arbitrarily) — a genuinely comparative question would get a one-sided, single-game-grounded answer with no signal to the user that the other game was dropped from scope. Fixed: `game_detector.detect_games()` (plural) now returns *every* game the question names; `retrieval_service.retrieve_candidates` scopes the Chroma query to all of them at once via `$in` (`chroma_service._game_where`) rather than one. The per-chunk `[GameName]` breadcrumb `chunk_service.py` already bakes into stored chunk text (see below) is what lets the model correctly attribute each retrieved chunk to the right game once both are in context — no prompt-template change was needed for that part. `effective_game_name` returned to the caller is still a single value (the most-mentioned game), since that's what `ChatHistory.game_name`/the next turn's `fallback_game` continuity expects — only the retrieval *scope* is multi-game aware. Regression tests: `rag_chat/tests.py:GameDetectorMultiGameTests`, `ChromaGameWhereTests`, `RetrieveCandidatesMultiGameTests`, `ChatApiTests.test_chat_question_naming_two_games_is_not_treated_as_ambiguous`.

**The very first message in a conversation names no game, and there's no history to fall back on.** *A real gap, found and fixed*: with `fallback_game=None`, retrieval used to run completely unscoped across every uploaded game's rulebook — an ambiguous question ("how many players are there?") could retrieve and rank chunks from the wrong game's rulebook ahead of the right one, purely on vector/keyword score, and the model could confidently answer from it with no indication the game was ever in doubt. Fixed: `ChatView.post()` now checks `detect_games(question)` *before* running any retrieval at all — if neither the question nor the conversation history names a game, it returns a clarifying response asking the user to specify one (naming a few of the platform's own catalog games as examples), and never touches embeddings/Chroma/Groq for that turn. Deliberately not saved as `ChatHistory` — there's no grounded answer or game context for a later turn to inherit. Regression tests: `rag_chat/tests.py:ChatApiTests.test_chat_ambiguous_question_asks_for_clarification_instead_of_guessing`/`test_chat_ambiguous_question_lists_known_games_as_examples`.

**A rulebook PDF that discusses multiple games in one document.** `chunk_service.py` doesn't tag chunks by whatever `Game` catalog entry the upload was filed under — it splits the document at "1. Introduction" boundaries (`_split_into_game_sections`) and runs `detect_game()` independently on *each section's own text*, tagging every chunk with whatever game that specific section is actually about. *Handled, and more capable than it might look from the upload UI alone*: a single upload attached to one catalog game can correctly seed retrievable content for several real games at once if the source document covers more than one — confirmed directly against this project's own uploaded corpus, where one such document ended up correctly tagged across seven distinct games, not the one game it was nominally filed under.

**An oversized rulebook section (a heading with unusually long text under it).** `chunk_service.py`'s `_oversized_heading_splitter` (`RecursiveCharacterTextSplitter`, token-length-aware via the same embedding model's tokenizer) only engages past `_HEADING_SPLIT_THRESHOLD` (700 tokens) — verified against the actual corpus this project has loaded, where the longest heading is ~490 tokens, so this path exists for future/larger documents rather than triggering on anything uploaded so far. *Handled, currently dormant.*

**Groq deprecates or removes the configured model.** *A real production incident, not a hypothetical*: `GROQ_MODEL` pointed at `llama-3.3-70b-versatile`, which Groq had removed entirely — every single chat request failed with a `404 model_not_found` from Groq's API, regardless of question or game, until diagnosed and repointed at a currently-available model. The fallback default baked into `groq_service.py` (used only if `GROQ_MODEL` is ever completely unset) pointed at a *second*, separately-deprecated model (`llama-3.1-8b-instant`) — meaning even the safety-net path would have failed identically. *Fixed*, but structurally still a live risk: nothing in this codebase validates that `GROQ_MODEL` names a model Groq currently serves, at startup or otherwise — this is an external vendor's decision the app has no visibility into ahead of time, and would fail the same way again if Groq deprecates whatever model is configured next. Worth periodically confirming the configured model against `GET https://api.groq.com/openai/v1/models` rather than assuming a pinned model name stays valid indefinitely.

**A chat request arrives before the embedding/reranking models have ever loaded in this process.** *Was a real production incident*: both `embedding_service.py` and `rerank_service.py` used to load their `sentence-transformers`/`CrossEncoder` models **at module import time** — and because `config/urls.py` wires every app's routes into one flat list, resolving *any* URL (including the unrelated `/api/core/health/` health check) forced Django to import the full `rag_chat` module chain and pay that loading cost. On a CPU-constrained deployment, that load was slow enough to exceed gunicorn's worker timeout, killing the worker mid-boot before it ever finished — and every replacement worker hit the identical wall, looping indefinitely with no request of any kind ever succeeding. *Fixed*: both models are now lazily instantiated on first actual use (a module-level cache, populated inside a `_get_model()` accessor), decoupling "the app can respond to any request at all" from "the RAG pipeline's models happen to be warm yet." Verified directly: importing the full URL chain now takes ~3 seconds with zero model loading; the first real chat request still pays the model-load cost once, but only that request, and only within the worker that happens to receive it.

**A rulebook chunk retrieved from Chroma with no matching game in the platform's tournament catalog.** `game_detector.py` matches against a hardcoded list of common esports titles (`_COMMON_ESPORTS_GAMES`) in addition to whatever `Game` rows exist in this platform's own catalog — so a rulebook can be usefully chunked and answered on for a game the platform doesn't (or doesn't yet) run tournaments for at all. *Handled, deliberate* — the RAG assistant's scope is "esports rules in general," not strictly limited to games this specific platform currently hosts.

## Account deletion & data integrity

**An approved organizer deletes their own account.** *A real bug, found and fixed*: `Organizer.user`/`Tournament.organizer` used to be `CASCADE` — self-deleting via `PlayerMeView` would silently take every tournament that organizer had ever run, and everything downstream (registrations, teams, brackets, matches, disputes) for every *other* participant, down with it. Fixed to `PROTECT`: the delete is refused outright, surfaced as a clear `400` rather than a cascading catastrophe or an unhandled `500`.

**A dispute's filer, an evidence uploader, or an admin-review requester deletes their account afterward.** `Dispute.filed_by`/`DisputeEvidence.uploaded_by`/`AdminReviewRequest.requested_by` are `SET_NULL`, not `CASCADE` — the dispute, its evidence, and the review decision all survive; only the "who did this" attribution becomes `null`. *Handled, deliberate* — these are accountability records other stakeholders rely on; "the account that did this is gone" is a different, correct fact from "this never happened."

**An anonymous request against an unpublished tournament whose creator account has been deleted.** *A real bug, found while writing a regression test for something else*: `Tournament.created_by` is `SET_NULL`, so a deleted creator leaves `created_by_id = None`. `IsPublicOrOwner`'s ownership check was a bare `tournament.created_by_id == request.user.pk` — and an anonymous request's `request.user.pk` is *also* `None`, so `None == None` incorrectly granted "owner" access to *any* unpublished tournament with a deleted creator, for literally anyone unauthenticated. Fixed by requiring `request.user.is_authenticated` before that comparison runs at all.

## File uploads

**A file whose bytes don't actually decode as the format its extension/`Content-Type` claims.** `validate_document_file` doesn't trust either — it magic-byte-sniffs *and then actually decodes* the file (Pillow `.verify()` for images, PyMuPDF for PDFs) inside a broad `except Exception` that rejects anything that doesn't genuinely parse. *Handled* — a file that merely starts with a valid JPEG/PNG/PDF signature but isn't real, decodable content of that type is rejected, not just waved through on a header check.

**A deliberately huge image dimension declared in an otherwise-small file (a decompression bomb).** Pillow's own `Image.MAX_IMAGE_PIXELS` check runs *before* any pixel data is decoded, raising `DecompressionBombError` — caught and turned into an ordinary `ValidationError`. *Handled*, and free (this is Pillow's own protection, not custom code).

**A PDF with an embedded file, or an unusually long PDF.** Page count capped at 30 (these are CNIC scans/certs/payment proofs — never legitimately long); any PDF with `embfile_count() > 0` is rejected outright, since embedded files have no legitimate purpose in this context and are a way to smuggle an unrelated payload inside an otherwise-valid PDF. *Handled.*

**An SVG upload.** Deliberately excluded from accepted formats entirely, despite being a real image format — the admin panel previews uploaded documents in an `<iframe>`, and an SVG can carry an executable `<script>`. *Handled as a specific stored-XSS mitigation*, not an oversight — don't add SVG back without addressing that risk directly.

**A signed document link (Cloudinary) leaking or being shared.** Every link is minted fresh per-request, only after the serving view's own ownership check passes, and expires after 600 seconds even if it does leak — there is no long-lived, guessable, or shareable link to a sensitive document anywhere in the system. *Handled.*

## Infrastructure & deployment

These aren't application-code edge cases, but they're this project's own real, recent operational incidents, each with a concrete lesson worth keeping visible rather than letting the postmortem knowledge evaporate.

**A platform-level "Docker Command" override silently bypasses the image's own boot sequence.** The production Render service had a custom Docker Command override set to run gunicorn directly — which, per Render's own documentation, replaces *both* the Dockerfile's `CMD` and `ENTRYPOINT`. Since `entrypoint.sh` is what actually runs `migrate --noinput`/`collectstatic` before the app starts, this meant **migrations silently never ran on any deploy**, indefinitely, with no error at deploy time — the app just served whatever schema state the database happened to already be in. *Fixed* by clearing the override so the Dockerfile's own boot sequence (which was always correct) actually runs. Worth a periodic check: a platform-level dashboard setting can silently override what the versioned Dockerfile says, with no diff/review step the way a code change gets.

**A cold-started free-tier instance combined with a synchronous, per-request-blocking email send.** Registration's OTP email send happens synchronously inside the request/response cycle (no task queue exists in this codebase at all — see `ARCHITECTURE.md#background-jobs`). Combined with a resource-constrained instance waking from an idle sleep, a user's first signup after a period of inactivity pays both costs stacked: the platform's own wake-up latency, plus however long Brevo's API takes to accept the send, before the response completes. *Understood, not architecturally fixed*: the keep-alive health-check workflow (`.github/workflows/health-check.yml`, pinging `/api/core/health/` every 10 minutes) mitigates the idle-sleep half of this; the synchronous-email-send half would need a background task queue to actually change, which is a real architectural addition, not a quick patch.

**Multiple gunicorn workers each loading heavy in-memory ML models on a memory-constrained instance.** The Dockerfile's default worker count (3) meant three separate processes each holding their own full copy of the embedding + reranking models in memory simultaneously — on a small instance, this was enough to trigger out-of-memory worker kills under real request load, independent of and in addition to the eager-import timeout issue documented above under the RAG chatbot section. *Fixed* by dropping to a single worker, matching what the platform's own `WEB_CONCURRENCY` default was already trying to signal (and which the Dockerfile's hardcoded `--workers 3` flag had been silently overriding). The real tradeoff this accepts: request handling is now fully sequential within that one process — acceptable at current traffic levels, worth revisiting (more RAM, not more workers with this same memory footprint) before traffic grows enough for that to bind.
