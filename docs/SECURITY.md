# Security

This documents how Esports Pakistan actually protects data and access today — grounded in the current code, not a generic checklist. For the system's overall shape, see [`docs/ARCHITECTURE.md`](ARCHITECTURE.md). For a pre-deploy checklist, see [`docs/SECURITY_CHECKLIST.md`](SECURITY_CHECKLIST.md). To report a vulnerability, see [the last section](#reporting-a-vulnerability).

## Authentication

Stateless JWT (`djangorestframework-simplejwt`) is the only API authentication class registered (`config/settings.py:DEFAULT_AUTHENTICATION_CLASSES`) — no session-cookie auth for the API.

- **Token lifetimes**: access tokens 1 hour, refresh tokens 7 days. `ROTATE_REFRESH_TOKENS=True` + `BLACKLIST_AFTER_ROTATION=True` — each refresh use invalidates the token that was just spent.
- **`SECRET_KEY` and `JWT_SECRET_KEY` are two separate required secrets** — signing JWTs with a different key than Django's general `SECRET_KEY` limits blast radius if one leaks. Neither has a code fallback; the app refuses to start if either is unset.
- **Session revocation**: `core/tokens.py:revoke_all_sessions(user)` blacklists every outstanding refresh token for that user. Called on password change and password reset — a stolen refresh token stops working the moment the account owner changes their password. Live access tokens are *not* individually revoked this way (they're stateless and expire within the hour by design). Also exposed directly as a self-service action: `POST /api/auth/logout-all/` (`core.views.LogoutAllSessionsView`) for a user who suspects a device they're not currently holding still has a valid session — surfaced in the frontend as "Log out of all devices" on the account settings page.
- **Password hashing**: BCryptSHA256 primary, PBKDF2 as a fallback verifier for any legacy hash. Don't reorder `AUTH_PASSWORD_HASHERS` without a migration plan — the first entry is what *new* hashes use, older hashes keep verifying against whichever entry actually produced them.
- **Password policy**: minimum length, common-password rejection, user-attribute similarity rejection, a 128-char maximum (bounds bcrypt CPU cost against a deliberately huge password), and `StrongPasswordValidator` (requires uppercase, lowercase, digit, and special character) — see `core/validators.py`.
- **Email verification is structural, not a flag.** Signup never creates a `User` directly — it creates a `PendingRegistration` (hashed password, not plaintext) and emails a signed token. Only clicking that link creates the real `User`. There is no `is_email_verified=False` account sitting in the database waiting to be "verified later" from the registration path; an unverified signup simply has no `User` row at all. (`is_email_verified` still exists as a field — used for Google-linked accounts, which are verified by Google directly, and settable on data created another way — but it is not what gates registration.)
- **Google OAuth** — the server verifies the client-supplied `id_token` itself via Google's own `google-auth` library (`google.oauth2.id_token.verify_oauth2_token`, `core/views.py:GoogleLoginView`). That single call is what checks signature, issuer, audience (against `GOOGLE_CLIENT_ID`), and expiry — nothing about the token is trusted from the client beyond the raw string. `email_verified` on the returned payload is checked separately before the email is trusted for linking/creating an account. Failure modes are split deliberately: a bad/expired/wrong-audience token is a `ValueError` from the library → 400 `ValidationError`; Google being unreachable is a `GoogleAuthError` → a distinct 503 (`GoogleAuthUnavailable`) so a network blip on Google's end isn't reported to the user as "your token was invalid."
  - **Account linking**: `User.objects.get_or_create(email=...)` — a password-based account can be silently linked to Google sign-in the first time its owner uses "Sign in with Google" and the Google-verified email matches exactly. This is intentional (same person, same email Google itself has verified), not a bypass: nothing about it lets a *different* person cause their Google account to attach to someone else's existing account, since the match is on Google's own verified `email` claim, not anything client-asserted.
  - **The nonce is server-verifiable, not just client-side.** `GET /api/auth/google/start/` (`core.views.GoogleOAuthStartView`) generates a random nonce and hands it back signed as `state` (`signing.TimestampSigner`, salt `google-oauth-state`, 5-minute max age). The frontend (`frontend/src/lib/googleAuth.js:startGoogleSignIn`) sends both `nonce` and `state` to Google as separate URL params; Google embeds `nonce` in the returned `id_token`'s own `nonce` claim and echoes `state` back verbatim in the callback fragment. `GoogleLoginView` re-derives the *expected* nonce by unsigning `state` itself — not by trusting anything the client asserts — and checks it against the token's claim (`core/views.py:GoogleLoginView.post`). A `state` is also single-use: once a login with it succeeds, `cache.set(f'google_oauth_state_used:{state}', ...)` blocks it from being replayed (`core/tests.py:GoogleLoginApiTests.test_google_login_state_cannot_be_replayed_after_a_successful_login`). This replaced an earlier design where the nonce was generated and checked entirely client-side — a client-side check can't actually prove anything to the server, since the same client controls both the "nonce it used" and the "nonce it expects."
  - **Known residual limitation**: this still doesn't bind a `state` to the specific browser tab that requested it — doing that properly needs either a same-site cookie (which would reintroduce the credentialed-cross-origin-CORS surface `CORS_ALLOW_CREDENTIALS=False` deliberately closed — see [CORS](#cors)) or migrating off implicit flow entirely to authorization-code+PKCE with a server-side code exchange. Practical impact: someone who completes their *own* legitimate Google sign-in flow through this app could in principle get their own valid `(state, id_token)` pair processed on a victim's browser via a crafted page (classic "login CSRF" — forces the victim's browser to end up authenticated as the attacker's account, not an account-takeover of the victim's own account). This is a well-known category of residual risk for implicit-flow OAuth generally, not specific to a mistake in this implementation; treat migrating to authorization-code+PKCE as the real fix, and as a deliberate future migration rather than something to bolt on reactively.
- **Account enumeration is avoided on purpose**: `ForgotPasswordView` returns an identical response whether or not the email exists; `ResendVerificationView` does the same.
- **Password reset / email verification token lifecycle** (both in `core/tokens.py`):
  - `password_reset_token` is Django's own `PasswordResetTokenGenerator` — HMAC-based and stateless (no DB row to leak/query), but *not* freely reusable: its hash is derived in part from `user.password`, so the moment `ResetPasswordView` calls `user.set_password(...)`, every token issued before that point stops verifying — a used reset link cannot be used a second time, and neither can any other unused link sent earlier. Expiry is Django's `PASSWORD_RESET_TIMEOUT` setting (default 3 days; not overridden in `settings.py`), checked inside `check_token`.
  - `pending_registration_token` (`PendingRegistrationTokenGenerator`) is single-use differently: `VerifyEmailView` deletes the `PendingRegistration` row inside the same transaction that creates the `User`, so a second click on the same verification link has no `PendingRegistration` left to look up at all — not "the token fails," but "the thing it points at no longer exists." Same default 3-day expiry window as above.
  - Both flows call `revoke_all_sessions(user)` / are structurally incapable of being replayed (see above), so there's no path where a reset token, once used, leaves any lingering valid session or itself remains valid.

## Authorization

Two mechanisms:

1. **Object-level permission classes** (`tourny_regist/permissions.py`, `games/permissions.py`, `partners/permissions.py`) — pattern: staff (`is_staff`) always passes; otherwise compare `request.user`/`request.user.organizer_profile` against the object's owner FK. `IsTournamentStaffOrAdmin` is the reference implementation this pattern is modeled on across the codebase.
2. **View-level `IsAdminUser`** — every endpoint that's entirely staff-gated with no object-level nuance (all `Admin*View` classes across `core`, `tourny_regist`, `organizer`, `dashboard`, `rag_chat`).

**Important nuance**: every DRF-layer admin check in this codebase tests `is_staff`, not `is_superuser`. Any staff user — not just a superuser — can use every `Admin*` API endpoint. `is_superuser` matters only for Django's own admin site (`/admin/`) internals, where it grants a blanket permission bypass Django itself implements. If you need a permission tier *between* "any staff member" and "full superuser" for a specific admin action, it does not exist today and would need to be built — don't assume `is_superuser` is checked anywhere in the API layer, because it isn't.

**Known limitation, deliberately not "fixed" reactively**: this means the blast radius of one compromised staff account is every `Admin*` endpoint — approve/reject tournaments and organizers, resolve disputes, manage rulebooks, edit any user. Splitting this into granular roles (e.g. `can_manage_tournaments`, `can_resolve_disputes`, `can_manage_organizers`) is a real, sizeable feature — it touches every `Admin*View` across `core`, `tourny_regist`, `organizer`, `dashboard`, and `rag_chat` — not a settings tweak, so it isn't something to bolt on as a side effect of a security pass. If the number of staff accounts grows, or staff accounts start being assigned to people outside a small trusted set, revisit this as its own project. In the meantime, the practical mitigation is operational: keep the staff list small and reviewed (see the [Admin surface checklist item](SECURITY_CHECKLIST.md#admin-surface)), since there is no in-app tier between "no admin access" and "all of it."

`core/admin_capabilities.py:HasAdminCapability` is a prepared extension point for that future rollout — a drop-in replacement for `permissions.IsAdminUser` on a *new* admin view that behaves identically today (any `is_staff` account passes) but takes a capability name (`manage_tournaments`, `manage_disputes`, ...) so adopting it early costs nothing and means the eventual real rollout is "start reading `capability` on `User`" rather than "touch every view's `permission_classes`." Nothing currently reads or enforces a capability — see that module's docstring before assuming it does more than it does.

**The single most consequential admin action — granting or revoking someone else's `is_staff`/`is_active` — requires re-entering the acting admin's own current password** (`core.views.AdminUserDetailView.update`, `current_password` in the request body, checked with `request.user.check_password`). A stolen-but-still-valid access token (XSS, an unattended browser) shouldn't be enough on its own to mint a second admin account or deactivate one; this doesn't require a *recent* login, just proof the caller still knows the admin's own password right now. Every such change is also recorded both in `AuditLog` (`action='admin.user_staff_status_changed'`, before/after state in `metadata`) and as a structured security event (see [Security monitoring](#security-monitoring) below) — this endpoint previously logged neither.

**No app has a `permissions.py` for `core`, `organizer`, `brackets`, or `dashboard`** — those gate access with stock DRF classes directly in `permission_classes`, plus inline ownership checks in view bodies (e.g. `organizer/views.py:_get_organizer(user)` always derives the organizer from `request.user`, never a URL parameter, so there is structurally no way to address another user's organizer profile).

### Admin-review escalation

The riskiest self-service actions (cancel a tournament, cancel a registration, reset a bracket) don't get a bigger permission gate — they get routed to a human. Each has a "is this safe?" check (e.g. "does this tournament have zero registrations and no bracket?"); if unsafe, the action doesn't happen at all — it raises `NeedsAdminReview`, which the view turns into an `AdminReviewRequest` row and a 202 response. An admin later approves or rejects it; approval re-invokes the *exact same* service function with the safety check bypassed, never a separate "admin version" of the logic. This means there is exactly one code path per dangerous action to audit, not two that could silently diverge. See [`docs/ARCHITECTURE.md#authorization-architecture`](ARCHITECTURE.md#authorization-architecture) for the full flow diagram.

## User data isolation

Enforced entirely at the Django/DRF layer (no database-level Row Level Security — see [Database security](#database-security)), consistently as "derive the object from `request.user`, don't trust a client-supplied identifier to point at someone else's data":

- **Tournaments**: `MyTournamentsView` filters by `created_by=request.user` server-side, not a client-supplied filter param.
- **Registrations**: a player can only delete/view their *own* registration (`registration.player_id == request.user.pk`, checked in `get_object()`, or `is_staff`).
- **Teams**: only the captain can delete a team or remove a member other than themselves.
- **Organizer profile**: every self-service organizer endpoint resolves `user.organizer_profile` (a `OneToOneField`) from `request.user` — there is no code path that accepts an organizer ID from the client for these endpoints.
- **Player profile**: `PlayerMeView` always returns `request.user`'s own row, regardless of any `pk` elsewhere in the request.
- **Disputes**: a non-stakeholder gets `404`, not `403`, on `DisputeDetailView`/`DisputeEvidenceUploadView` — deliberately, so a bad guess doesn't confirm the dispute exists at all.
- **Audit log**: `AuditLog` has no generic "browse everything" endpoint. The only read paths (`TeamHistoryView`, `RegistrationHistoryView`) are scoped to one object the requester already manages, specifically so audit history can't be used to enumerate objects outside the requester's authority. Separately from read-access scoping, **`AuditLog` is append-only at the model layer** (`core/models.py`): `save()` raises `ValueError` if called on a row that already has a `pk` (i.e. an update, as opposed to the initial insert `core.audit.log_action` performs), and `delete()` raises unconditionally. There is no API path today that edits or deletes an entry — this is the backstop against one being added by mistake later (a generic admin viewset, a Django-admin registration without restricted fieldsets, etc.), not a response to an existing gap. See `core/tests.py:AuditLogImmutabilityTests`.
- **File access**: see [File uploads](#file-uploads) — there is no raw, guessable URL to a sensitive document; every link is minted fresh, per-request, only after the serving view's own ownership check passes.

### IDOR audit — two real gaps found and fixed

A systematic pass over every object-detail/action endpoint in `core`, `organizer`, `tourny_regist`, `brackets`, `games`, `partners`, `dashboard`, and `rag_chat` (checking, per endpoint: how the object is fetched, and whether an ownership/staff check actually runs before it's returned or mutated) found the isolation pattern above holding almost everywhere it's supposed to — with two exceptions, both in `tourny_regist`, both now fixed:

- **`GET /api/tournaments/<pk>/rules/`** (`TournamentRulesView`) was `AllowAny` with no visibility check at all — an unauthenticated client could read a draft/pending/unpublished tournament's rules (and the real email of whoever published them, via a `created_by_email` field) just by guessing the tournament ID. Fixed to use the same `IsPublicOrOwner` gate `TournamentDetailView` already used (staff, the owning organizer, or public once `APPROVED`+published) — matching what the view's own docstring had claimed all along but the code didn't actually enforce. `created_by_email` is gone; replaced with `created_by_name` (via the same non-PII `display_name()` fallback described below), since the endpoint's audience is now broader than just staff/organizer once a tournament is published.
- **`GET /api/tournaments/<pk>/announcements/`** (`TournamentAnnouncementsView`) required only `IsAuthenticated` — any logged-in account, not a stakeholder in *that* tournament, could list announcements for a draft/pending/unpublished tournament ID it had no relationship to. Fixed the same way (`IsPublicOrOwner` added to the GET permission set, with `check_object_permissions` called from `get_queryset()` since a list endpoint has no single object DRF checks this against automatically). Separately, `AnnouncementSerializer`'s `author_name` fell back to the author's real email when they had no first/last name set (`tourny_regist/serializers.py:display_name`) — visible to that same broad, non-stakeholder audience. Hardened to match `brackets/serializers.py`'s own `display_name()`, which never falls back to an email for exactly this reason (bracket/match data has the same "visible to any authenticated user" audience) — the `tourny_regist` copy just hadn't been given the same treatment.
- **A latent bug found while writing the regression test for the fix above**: `IsPublicOrOwner.has_object_permission`'s ownership check was `tournament.created_by_id == request.user.pk`. `Tournament.created_by` is `SET_NULL` (survives the creator's account being deleted — see [Account deletion & data integrity](#account-deletion--data-integrity)), and an anonymous request's `request.user.pk` is *also* `None` — so `None == None` incorrectly granted "owner" access to *any* unpublished tournament whose creator's account had been deleted, for literally anyone. Fixed by requiring `request.user.is_authenticated` before that comparison runs at all (`tourny_regist/permissions.py`). Regression test: `tourny_regist/tests.py:TournamentRulesTests.test_anonymous_request_not_treated_as_owner_of_a_tournament_with_no_creator`.

Everything else audited — team join/leave/lock/unlock/substitute, registration check-in/disqualify/cancel/review, match result/override/forfeit/schedule/notes, admin review-request decide, and every endpoint that takes an object ID from the request *body* rather than the URL (`TeamSubstituteView`, `TournamentSeedingView`, `MatchResultSerializer`/`MatchOverrideSerializer`/`MatchForfeitSerializer`) — already scoped the lookup and/or verified ownership correctly. `brackets`' spectator endpoints (`TournamentBracketView`, `TournamentMatchesView`, `MatchDetailView`) let any authenticated user view bracket/match data regardless of tournament publish status — this is deliberate and already tested that way (`brackets/tests.py:test_get_bracket_any_authenticated_user` and neighbors, `brackets/serializers.py:display_name`'s own comment), not something this pass changed; flagging it here only because it's a real product-scope decision worth someone consciously owning rather than an accident.

## CSRF

`CsrfViewMiddleware` is active, and `CSRF_TRUSTED_ORIGINS` is environment-driven (`config/settings.py`, default `http://localhost:5173`). In practice this matters for **Django admin** (`/admin/`, session-cookie based) and any Django form view — not for the JWT API. The API authenticates via a bearer token read from the `Authorization` header; the browser never auto-attaches that header to a cross-site request the way it would a cookie, so classic CSRF does not apply to `/api/*` under this auth scheme. Don't add `@csrf_exempt` anywhere on the API believing it's "fixing" a CSRF problem — there isn't one there to fix, and the setting that *does* matter for the API's cross-origin behavior is CORS, below.

## CORS

`django-cors-headers`, explicit allow-list via `CORS_ALLOWED_ORIGINS` (env `CORS_ORIGINS`), **not** `CORS_ALLOW_ALL_ORIGINS` — that setting isn't used anywhere in this codebase, and should stay that way. Production must set `CORS_ORIGINS` to the real frontend origin(s) only; the dev default is `http://localhost:5173`.

`CORS_ALLOW_CREDENTIALS = False`. The frontend authenticates purely via a bearer token in the `Authorization` header (`frontend/src/lib/api.js`) — no view relies on a cross-site cookie, so there's nothing for credentialed CORS to legitimately unlock. The frontend's `fetch()` calls previously passed `credentials: "include"` (a leftover with no cookie behind it to include) — that's been removed to match, so a browser now never attaches cookies to a cross-origin request to this API even if one were accidentally set later.

## JWT

Covered under [Authentication](#authentication) above. Two implementation details worth calling out separately:

- **SimpleJWT is pinned to `ALGORITHM: 'HS256'`** (`config/settings.py:SIMPLE_JWT`) explicitly, rather than relying on the library's own default — a symmetric algorithm here always means `SIGNING_KEY`, never a keypair, and pinning it means a future settings change can't silently widen what's accepted. `AUDIENCE`/`ISSUER` claims aren't set — there's exactly one signer and one relying party (this API), so they wouldn't add a real boundary the way they do in a multi-service/multi-audience setup. Refresh tokens can't be used where an access token is expected and vice versa — SimpleJWT enforces this itself via the `token_type` claim inside `JWTAuthentication`, not something this codebase implements separately.
- **Tokens live in `localStorage`** (`esp_token`/`esp_refresh`, per `frontend/src/lib/api.js`), not an httpOnly cookie. That's a deliberate tradeoff that goes with the bearer-token/no-CSRF-surface design above — it does mean a successful XSS on the frontend can read both tokens directly, which is the single largest architectural security tradeoff in this codebase. Current mitigations: React/JSX auto-escaping (no `dangerouslySetInnerHTML` use should be introduced without real scrutiny), and a Content-Security-Policy restricting script sources to `'self'` (see [Security headers / CSP](#security-headers--csp) below) — CSP doesn't prevent XSS from a vulnerability in first-party code, but it substantially limits what a successful injection can actually load or exfiltrate to. **This has not been re-architected to httpOnly-cookie refresh tokens** — that's a real option (access token in memory, refresh token in an httpOnly+Secure+SameSite cookie) but it changes the CSRF model (a cookie-backed refresh endpoint needs its own CSRF protection, unlike the bearer-token API today) and is a breaking change to the auth contract between frontend and backend. Treat it as a deliberate future migration to scope and schedule, not a gap to silently patch around.

## Security headers / CSP

- **Backend (Django-served responses — `/admin/`, API error pages, `/secure-media/`)**: `SecurityMiddleware` sets `X-Content-Type-Options: nosniff` (`SECURE_CONTENT_TYPE_NOSNIFF = True`), `Referrer-Policy: strict-origin-when-cross-origin` (`SECURE_REFERRER_POLICY`), and HSTS (`SECURE_HSTS_SECONDS` etc., see [Production DEBUG/ALLOWED_HOSTS/HTTPS](#core-django-settings) in the checklist). `XFrameOptionsMiddleware` sets `X-Frame-Options: DENY` (`X_FRAME_OPTIONS = 'DENY'`) globally, with one deliberate exception: `secure_media_view` and the dev-only media route are `xframe_options_exempt`'d so the admin panel can preview uploaded documents in an `<iframe>` — see [File uploads](#file-uploads).
- **Frontend (the actual XSS-relevant surface — this is where user-generated content renders)**: `frontend/index.html` ships a `<meta http-equiv="Content-Security-Policy">` restricting `script-src`/`default-src` to `'self'`, `object-src` to `'none'`, and scoping `style-src`/`font-src`/`img-src`/`connect-src` to what the app actually needs (Google Fonts, the API origin, Cloudinary-hosted images). A meta-tag CSP cannot express `frame-ancestors` — browsers silently ignore that directive there — so it's set at the HTTP-header level instead: `frontend/vercel.json`'s `headers` block (Vercel deploys) and `frontend/nginx.conf`'s `add_header` directives (self-hosted/Docker deploys) both add `Content-Security-Policy: frame-ancestors 'none'` plus `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, and `Permissions-Policy`. `Strict-Transport-Security` is set at the Vercel-header level (where TLS is actually terminated) but deliberately not in `nginx.conf`, which listens on plain HTTP inside the Docker network — an HSTS header over HTTP is a no-op at best and misleading at worst if that container is ever exposed directly.

## Rate limiting

DRF `ScopedRateThrottle`, rates centralized in `config/settings.py:DEFAULT_THROTTLE_RATES` — **add new rate-limited endpoints here, don't hardcode a rate inline in a view.**

| Scope | Rate | Protects |
|---|---|---|
| `login` | 10/min | Password login, Google login (per client IP) |
| `login_email` | 10/min | Password login (per submitted email — see below) |
| `register` | 20/hour | Registration |
| `email_action` | 5/hour | Forgot/reset password, verify/resend-verification email (per client IP) |
| `email_action_email` | 5/hour | Forgot password, resend-verification (per submitted email — see below) |
| `chat` | 20/min | RAG chat assistant |
| `team_join` | 20/min | Joining a team by invite code |
| `user` | 1000/min | Every authenticated request (global ceiling) |
| `anon` | 200/min | Every anonymous request (global ceiling) |

`user`/`anon` are global floors that apply everywhere regardless of scope; the named scopes are additional, tighter limits on specific sensitive actions.

**Per-account throttling, layered on top of per-IP** (`core/throttling.py`): every scope above except `login_email`/`email_action_email` is keyed by client IP (DRF's default). An IP-only limit doesn't stop credential stuffing or a reset-link mail-bomb distributed across many IPs against *one* account — `LoginEmailRateThrottle` and `EmailActionEmailRateThrottle` key their cache entry off the submitted `email` field instead, and are wired in alongside the IP-scoped throttle on `LoginView`, `ForgotPasswordView`, and `ResendVerificationView` (`core/views.py`). `core/tests.py:LoginApiTests.test_login_throttled_per_account_even_across_different_ips` exercises this directly — 10 failed attempts against one account from 10 different IPs, then an 11th that gets a 429 even though no single IP in that sequence went past 1 request. Registration doesn't get an equivalent per-email throttle: repeat registration attempts for the same email hit `PendingRegistration.objects.update_or_create` (`core/serializers.py`), not a new row each time, so there's no per-email amplification to bound beyond the existing per-IP `register` scope.

**Throttle storage / cache backend**: DRF throttling reads and writes its counters through Django's cache framework. Without `REDIS_URL` set, `config/settings.py` leaves the default `LocMemCache` in place, which is **per-process** — behind more than one gunicorn worker or more than one instance, each process keeps its own counter, so the effective rate is (configured rate) × (worker/instance count), not the configured rate. Set `REDIS_URL` in production; `settings.py` switches to Django's built-in `RedisCache` backend automatically when it's present (the `redis` package is in `requirements.txt` for this). This is genuinely a checklist item, not a code guarantee — see [`SECURITY_CHECKLIST.md`](SECURITY_CHECKLIST.md).

## Secrets

- **Loading**: mostly `django-environ` (`env('X')`/`env.bool(...)`/`env.list(...)`), with a handful of values (`CLOUDINARY_*`, `GROQ_API_KEY`) read via plain `os.getenv()` instead — two mechanisms coexist rather than one consistently, worth knowing if a new secret doesn't seem to be picked up (check which loader the surrounding code in that file actually uses).
- **`.env` is gitignored** (`.env`, `.env.*`, with `.env.example` explicitly re-allowed). `backend/.env` exists locally and is never committed.
- **No secret is logged**. `SECRET_KEY`/`JWT_SECRET_KEY` never appear in any log call. `logger.exception(...)` calls around email/upload/token failures log the exception and a row ID, not credentials or token values.
- `ANTHROPIC_API_KEY` and `REDIS_URL` are now listed in both `.env.example` files (root, for `docker compose`, and `backend/`, for running the backend directly) — previously `ANTHROPIC_API_KEY` was read by `config/settings.py` but missing from both, so anyone provisioning a new environment from the example file alone would silently miss it. If you add a new secret read via `env()`/`os.getenv()`, add it to both `.env.example` files in the same change, not as a follow-up.
- **`AuditLog.metadata` is a free-form JSONField** (`core.audit.log_action(..., **metadata)`). No current call site passes anything sensitive into it, but nothing stops a future one from accidentally logging a request body or token into permanent audit storage — treat this as a rule, not just a fact: **never pass raw request bodies, passwords, or tokens into `log_action`'s metadata kwarg.**
- **Console email backend leaks tokens to logs in dev.** The dev-default `EMAIL_BACKEND` (console) prints the full email body — including the verification/reset link with its signed token — to stdout. This is expected and harmless in local dev, but would be a real problem if a production deployment were ever accidentally left on the console backend (see the checklist).

## Admin permissions

Django admin (`/admin/`) is separate from the DRF API's admin views and uses Django's own session-based auth. `is_staff` grants admin-site login; `is_superuser` (via `PermissionsMixin`) grants a blanket Django permission bypass inside `/admin/` specifically. Only `User` and `Follow` are registered in Django admin — every other admin workflow (tournament approval, organizer approval, dispute resolution, review-request decisions, RAG rulebook management) happens through dedicated DRF `Admin*` endpoints instead, all gated by `IsAdminUser` (i.e., `is_staff`, not `is_superuser` — see the nuance under [Authorization](#authorization) above).

`AdminUserDetailView` specifically blocks an admin from removing their own `is_active`/`is_staff` flag via the API — a guard against an admin locking themselves out (or being tricked into it) through the normal edit endpoint.

## Database security

PostgreSQL via `DATABASE_URL_DEV`/`DATABASE_URL_PROD`, switched on `ENVIRONMENT`. **No Row Level Security** — every access-control decision in this system happens at the Django/DRF layer (permission classes, `get_queryset()` scoping, explicit ownership checks), not the database layer. This means: a bug in a view's permission check is a real, exploitable authorization bug with nothing underneath to catch it — there's no defense-in-depth database policy backstopping application logic. Keep this in mind when reviewing changes to `get_queryset()` or permission classes; they're the *only* layer, not one of several. Introducing RLS would be a genuine architecture change (policies per table, a Postgres role model distinct from the Django ORM's own connection user) — treat it as a deliberate future decision, not something to bolt on incidentally.

**Encryption in transit is now enforced, not just documented**: `config/settings.py` sets `sslmode=require` on the parsed `DATABASE_URL_PROD` connection options whenever `ENVIRONMENT == 'production'`, unless the URL itself already specifies a `sslmode`/`ssl` param (in which case that value is left alone — this fills the gap, it doesn't override an intentional choice like `verify-full`). Before this, an operator who deployed `DATABASE_URL_PROD` without an `sslmode` param would get a working, silently-plaintext connection with nothing anywhere raising a flag.

## Account deletion & data integrity

`PlayerMeView` (`/api/players/me/`) and `PlayerDetailView` (`/api/players/<pk>/`, admin-only) both allow a hard `DELETE` of a `User` row. Two categories of FK behavior on `User` matter here, and previously didn't get this distinction:

- **A real bug, now fixed**: `Organizer.user` and `Tournament.organizer` were both `CASCADE`. An approved organizer could self-delete their own account via `PlayerMeView` and silently take *every tournament they had ever run* — and everything downstream of those (registrations, teams, brackets, matches, disputes) for every *other* player who had participated — down with it, with no confirmation beyond the normal "delete my account" flow. Both are now `PROTECT`: Django refuses the delete outright rather than cascading. `core.views.ProtectedUserDeleteMixin` (used by both `PlayerMeView` and `PlayerDetailView`) turns the resulting `ProtectedError` into a clear 400 ("This account has an organizer profile with tournaments on record and cannot be deleted") instead of an unhandled 500. Regression tests: `core/tests.py:PlayerApiTests.test_organizer_with_tournament_cannot_self_delete` / `test_admin_cannot_delete_organizer_with_tournament_via_id`.
- **Accountability records survive the actor being deleted, by design**: `Dispute.filed_by`, `DisputeEvidence.uploaded_by`, and `AdminReviewRequest.requested_by` are all `SET_NULL` (not `CASCADE`) — same pattern already used for `Tournament.cancelled_by`/`champion`, `Dispute.resolved_by`, and `AdminReviewRequest.decided_by`. A dispute's resolution, its evidence, and an already-decided admin review are records other stakeholders (the opposing player, the organizer, staff) rely on — none of them should vanish because whoever filed/uploaded/requested it later deletes their account. `filed_by`/`uploaded_by`/`requested_by` becoming `null` on the row means "the account that did this is gone," not "this never happened." See `core/tests.py:AccountDeletionPreservesAccountabilityRecordsTests`.

## Concurrency

No database-level advisory locking beyond standard row locks (`SELECT ... FOR UPDATE` via Django's `select_for_update()`), used consistently at every check-then-act state transition that matters — a permission check answers "is this request allowed to try," a lock answers "did this request's read of the current state stay true long enough to act on it," and this codebase needs both, not just the first. See [`docs/ARCHITECTURE.md#concurrency-rules`](ARCHITECTURE.md#concurrency-rules) for the bracket engine's lock-ordering rules specifically (`brackets/services.py`), which predate this security pass and are the most mature example — `brackets/tests.py` has dedicated `TransactionTestCase`-based concurrency tests (real threads against a real database, since a single wrapped transaction can't exercise lock contention) for match completion, bracket generation, and Swiss/group-stage progression.

**A real gap found and fixed**: `RegistrationCreateView` (individual/solo registration — team-based registration's `TeamRegisterView` already did this correctly) checked `tournament.registrations.count() >= tournament.max_participants` without holding any lock, so two simultaneous registrations near the last open slot could both read "under the cap" and both succeed, overselling the tournament. Fixed by locking the `Tournament` row (`Tournament.objects.select_for_update()`) inside a `transaction.atomic()` block wrapping the whole validate-then-create sequence, mirroring `TeamJoinView`'s existing lock on the `Team` row for the identical race on team-roster slots. The *duplicate*-registration case (same player registering twice) has always had its own independent backstop regardless of locking: `Registration.Meta`'s `UniqueConstraint(fields=['tournament', 'player'])`. Regression test (real threads, not a single-transaction simulation): `tourny_regist/tests.py:RegistrationCapacityConcurrencyTests`.

**A second real gap, found during a follow-up business-logic audit**: `TeamCreateView` and `TeamJoinView` each locked only the *team* row they were directly touching (a brand-new team doesn't exist yet to lock; an existing team's own row for joining) — neither serialized against the other. A player could create team A and join team B at the same instant, since each request's "am I already on a team for this tournament?" check ran before either had committed the other's membership. Fixed by having both lock the *Tournament* row instead — the same broadened-scope tradeoff `RegistrationCreateView`/`TeamRegisterView` already made for their own capacity checks, now applied consistently to team-membership formation too. Regression test: `tourny_regist/tests.py:TeamMembershipConcurrencyTests`.

Other check-then-act transitions already correctly locked before this pass: `TeamRegisterView` (`Tournament` row), `AdminReviewRequestDecideView` (`AdminReviewRequest` row, `tourny_regist/views.py`), and everything in `brackets/services.py` per its documented lock order. `tourny_regist/lifecycle.py`'s tournament-lifecycle functions (`cancel_tournament`, `reschedule_tournament`, ...) lock the `Tournament` row internally (`_lock_tournament`) regardless of which view calls them — see [Service-layer invariants](#service-layer-invariants) below for why that matters beyond just concurrency.

## Service-layer invariants

The admin-review escalation pattern (see [Authorization](#authorization) above) means a service function like `tourny_regist.lifecycle.cancel_tournament` gets called from *two* places: the normal self-service view, and admin approval re-invoking the exact same function with `bypass_safety_check=True`. That only stays safe if the safety check genuinely lives *in the function*, not in whichever view happens to call it first — a future third call site (a bulk-admin action, a management command, a Celery task) needs the same protection automatically, without having to remember to reimplement it.

`tourny_regist/tests.py:ServiceLayerInvariantTests` exercises this directly: it calls `lifecycle.cancel_tournament(tournament_with_registrations, actor, reason)` with no view in between and asserts it still raises `NeedsAdminReview` — proving the invariant is enforced by the function itself, not merely by the one view currently gating access to it. Most of the lifecycle/service layer already had equivalent coverage indirectly (the HTTP-layer tests that assert a `202`+`AdminReviewRequest` response are, underneath, exercising this exact same code path — they're not mocked), but a direct call bypassing the view is a strictly stronger claim, and the pattern above is there to extend to `disqualify_registration`, `reset_bracket`, and similar functions as they're touched.

## Business-logic / state-machine invariants

Distinct from IDOR (does this user own the object) and concurrency (did the state stay true long enough to act on): even a stakeholder acting entirely within their own authority, one request at a time, can push an object through a sequence of legitimate-looking operations that should be unreachable. A follow-up audit specifically targeted this — every state-changing endpoint's `get_permissions`/serializer `validate()`, checked for whether it actually constrains *which* states a transition is allowed from, not just *who* can attempt it. `tourny_regist.lifecycle`/`brackets.services`'s own functions (`cancel_tournament`, `cancel_registration`, `reset_bracket`, `complete_match`) were already confirmed correct — every gap found was in a view/serializer that mutates state *directly*, bypassing those functions and their guards entirely.

- **`RegistrationDeleteView`** (a player's own hard-delete self-withdrawal, distinct from `lifecycle.cancel_registration`'s soft-cancel) had no state check at all — a player could delete their own registration after being seeded into a live bracket match (even after *winning* one), orphaning the opponent's match with no forfeit recorded, then immediately re-register with a clean row — evading the very admin-review gate `cancel_registration` enforces for exactly this "already played" case. Fixed: blocked entirely (for the player *and* for staff, via the same endpoint) once `hasattr(tournament, 'bracket')` — past that point, withdrawal must go through `disqualify_registration`/`cancel_registration`, which know how to unwind a live match. Regression test: `tourny_regist/tests.py:TournamentRegistrationApiTests.test_cannot_hard_delete_a_registration_once_a_bracket_exists`.
- **`RegistrationCheckInView`** had two separate gaps:
  - Its terminal-status blocklist only covered `REJECTED`; `DISQUALIFIED`/`CANCELLED` registrations could be checked back in whenever `registration_fee == 0` (the field's default — true for most tournaments), since the only other gate (`status != APPROVED`) is itself conditioned on `registration_fee > 0`. A disqualified player — already forfeited out of their bracket match by `disqualify_registration` — could be checked back in as if nothing had happened. Fixed: `DISQUALIFIED`/`CANCELLED` now blocked unconditionally, same as `REJECTED`.
  - No check on bracket existence at all. `brackets.services.standings()`/`generate_next_swiss_round()` re-derive the eligible player pool *live* from whichever registrations are currently `checked_in`, not a roster frozen at bracket-generation time — so a late check-in after a bracket exists injects a player who never played earlier rounds into a later one, and an un-check-in silently drops a player with a completed, won match with no forfeit. Fixed: check-in status is frozen (both directions) once `hasattr(tournament, 'bracket')`; removing a bracket-era participant has to go through `disqualify_registration`. Regression test: `tourny_regist/tests.py:TournamentRegistrationApiTests.test_checkin_status_frozen_once_a_bracket_exists`.
- **`RegistrationReviewSerializer`** (organizer approve/reject of a registration's payment/entry) had no whitelist of valid status transitions at all — unlike its sibling `AdminTournamentUpdateSerializer.validate_status`, which explicitly restricts admin decisions to `PENDING → APPROVED/REJECTED`. A plain `PATCH {"status": "approved"}` could silently reinstate a `DISQUALIFIED` registration (undoing a forfeit's implications without undoing the forfeit) or a `CANCELLED` one (possibly one that only reached that state via an admin-approved review, because the player had already played), with no reason required and no link back to why the original decision was made. Fixed: `DISQUALIFIED`/`CANCELLED` are now terminal from this endpoint's perspective — matches how `core.views.DisputeStatusView` treats `RESOLVED`/`DISMISSED`. (Reviewing an already-`APPROVED` registration to `REJECTED`, or vice versa, is still allowed — that's an existing, intentional, tested flow, e.g. discovering a fraudulent payment proof after initially approving it; only the two forfeit/admin-review-backed terminal statuses are now frozen.) Regression tests: `tourny_regist/tests.py:TournamentRegistrationApiTests.test_cannot_review_a_disqualified_registration`/`test_cannot_review_a_cancelled_registration`.
- **`TournamentUpdateSerializer`** allowed editing `game`, `team_size`, and `bracket_format` at any tournament status, including after registrations/teams/a bracket already existed — invalidating already-collected data (a roster sized for the old `team_size`, a bracket built for the old format). Concretely reachable: register a team with exactly `team_size` members (the only way `TeamRegisterView` allows it), then raise `team_size` via a tournament edit, then `TeamJoinView`'s capacity check has room again — a new player joins a roster the organizer had already submitted. Fixed: these three fields are frozen once the tournament has any registration, any team, or a bracket; `DRAFT` tournaments (nothing to invalidate yet) are unaffected, and resending a field's *unchanged* value (the frontend always resends the full form) never trips the check — only an actual change does. Regression tests: `tourny_regist/tests.py:TournamentUpdateValidationTests.test_team_size_cannot_change_once_a_team_has_registered`/`test_team_size_editable_before_anyone_has_registered`.
- **Duplicate `AdminReviewRequest` rows from a retried/double-clicked cancel button**: `TournamentCancelView`/`RegistrationCancelView`/`TournamentBracketResetView` each created a fresh `AdminReviewRequest` on every call that hit `NeedsAdminReview` — not itself a security bug (approving any one of the duplicates still re-locks and re-checks current state; approving a second stale duplicate afterward correctly 400s as "already cancelled"), but a real "duplicate submissions caused by retries" hygiene gap that queues up busywork for an admin. Fixed with the DB-constraint-first approach: `AdminReviewRequest.Meta` now has a partial `UniqueConstraint` (`content_type`, `object_id`, `request_type`, `condition=status='pending'`) — at most one pending request per target+type — and all three call sites catch the resulting `IntegrityError` and still return their normal `202`, so a retry is a clean no-op rather than an error or a duplicate. Regression test: `tourny_regist/tests.py:TournamentCancellationTests.test_repeated_cancel_clicks_do_not_queue_duplicate_review_requests`.
- **`DisputeEvidenceUploadView`/`DisputeEscalateView`** had no check on `Dispute.status` at all, unlike their sibling `DisputeStatusView`, which already correctly refuses further action once `RESOLVED`/`DISMISSED`. A stakeholder could keep attaching "evidence" to, or attempt to escalate, a dispute whose decision was already final. Fixed to match `DisputeStatusView`'s existing check. Regression tests: `core/tests.py:DisputeEvidenceTests.test_cannot_upload_evidence_to_a_resolved_dispute`, `DisputeEscalationTests.test_cannot_escalate_a_resolved_dispute`.

**Reviewed and deliberately left alone**: `MatchScheduleView`/`MatchNotesView` (scheduling metadata and organizer-private notes — neither affects match outcome/advancement/bracket eligibility, and retroactively noting something about a completed match is plausibly intended, not a bug); `AdminOrganizerUpdateSerializer` lacking `AdminTournamentUpdateSerializer`'s from-`PENDING`-only restriction (checked against the existing test suite — `organizer/tests.py:test_approve_clears_previous_rejection_reason` explicitly exercises re-approving a *previously rejected* organizer directly, so unlike the tournament case, this is intentional product behavior, not an inconsistency to fix — confirmed by attempting the analogous guard and having it break that test).

## File uploads

Every sensitive document (organizer CNIC scans, compliance certificates, payment proofs, dispute evidence) goes through `core/storage.py:CloudinarySignedStorage`, which:

- Uploads as Cloudinary's `authenticated` resource type — Cloudinary itself refuses to serve the asset without a valid signature, independent of anything Django does.
- Never returns a raw Cloudinary URL from `.url()`. It returns a short-lived internal signed link (`django.core.signing.TimestampSigner`, 600-second max age) that only redirects to a freshly-minted Cloudinary signed URL *after* the serving view's own permission check passes.
- So: there is no long-lived, guessable, or shareable link to a sensitive document anywhere in the system. A link is only ever generated per-request, after authorization, and expires in ten minutes even if leaked.
- **The signed link is already bound to one specific file, not a generic capability grant**: `TimestampSigner(...).sign(name)` signs the Cloudinary `public_id` itself (`core/storage.py:CloudinarySignedStorage.url`), and `secure_media_view` (`core/views.py`) unsigns that exact value and uses it — unmodified — as the `public_id` it mints a fresh Cloudinary URL for. There's no separate "access token" whose payload could be replayed against a different file's path; the token *is* the (signed) path.

**Upload validation** (`core/validators.py:validate_document_file`) is content-sniffed, not filename/`Content-Type` based (both are trivially spoofable): a 10MB size cap, a magic-byte check against exactly three allowed formats (JPEG, PNG, PDF), and — beyond the magic-byte sniff — the file is actually decoded before being accepted:
  - **Images** (`_validate_image_content`): opened and `.verify()`'d with Pillow. This rejects a file that merely starts with a JPEG/PNG signature but isn't a real decodable image, and gets Pillow's own decompression-bomb protection for free — `Image.open()` checks the declared width×height against `Image.MAX_IMAGE_PIXELS` before any pixel data is decoded and raises `DecompressionBombError` past that threshold, which is caught and turned into a `ValidationError`.
  - **PDFs** (`_validate_pdf_content`): opened with PyMuPDF (`fitz` — the same library the RAG pipeline uses to parse rulebooks), inside a broad `except Exception` that rejects anything PyMuPDF itself can't parse cleanly. Page count is capped at 30 (`_PDF_MAX_PAGES` — these are CNIC scans/certs/payment proofs/dispute evidence, never legitimately long), and a PDF with any embedded file (`doc.embfile_count() > 0`) is rejected outright — embedded files have no legitimate use in this context and are a way to smuggle an unrelated payload inside an otherwise-valid PDF.
  - Test fixtures for these paths (`core/tests.py`, `organizer/tests.py`, `tourny_regist/tests.py`) generate genuinely decodable JPEG/PDF bytes via Pillow/PyMuPDF rather than bare magic-byte stubs, so a regression in this validation would actually fail a test, not just look plausible.
  - **SVG is deliberately excluded** even though it's an image format — the admin panel previews these documents in an `<iframe>`, and an SVG can carry an executable `<script>`; excluding it is a specific stored-XSS mitigation, not an oversight. Don't add SVG to the allowed-formats list without addressing that.

The only unauthenticated, locally-served media are cover images and game logos (genuinely public assets) — served via Whitenoise/Django's static file handling, not through the signed-URL path, and correctly so: nothing sensitive goes through that route. Rulebook PDFs uploaded via `rag_chat` for the AI assistant go through a separate path (admin-only upload, not `validate_document_file`) — lower risk than the above since only staff can upload one, but worth knowing it isn't the same validation path.

## Redirects

The only server-issued redirect anywhere in the backend is `core/views.py:secure_media_view`'s `HttpResponseRedirect(cloudinary_url)` — and `cloudinary_url` there is always a freshly server-minted Cloudinary signed URL (see [File uploads](#file-uploads)), never anything derived from a client-supplied parameter. There is no `next=`/`redirect=`/`return_url=`-style parameter accepted anywhere in the codebase that feeds into a redirect target — verified by grepping the backend for redirect calls and query-param-driven URL construction, not just asserted. If a feature ever needs a post-login/post-action redirect, validate the target against an allow-list before this stops being true.

## Dependency scanning

`.github/dependabot.yml` runs weekly update checks against `backend/` (pip), `frontend/` (npm), and the GitHub Actions workflows themselves. This project processes PDFs, images, OAuth tokens, and third-party API responses through a fairly deep dependency tree (Django/DRF, SimpleJWT, Pillow, PyMuPDF, google-auth, Cloudinary, ChromaDB, Groq, ...) — a vulnerable dependency there can undermine otherwise-correct application code, so keeping these current isn't optional hygiene.

`.github/workflows/ci.yml`'s `container-scan` job runs Trivy (filesystem mode) on every push/PR — scanning both dependency lockfiles *and* both `Dockerfile`s (misconfig checks, e.g. running as root — neither image does; `backend/Dockerfile` explicitly drops to a non-root `appuser`) for known CVEs and secrets. This complements Dependabot rather than replacing it: Dependabot only checks on its own weekly schedule, so a CVE disclosed the day after a Dependabot run wouldn't surface until the next one — Trivy running on every push closes that gap. **Currently report-only** (`exit-code: 0`) — a dependency tree this size (`torch`, `transformers`, `chromadb`, ...) will very likely surface an existing backlog of CRITICAL/HIGH findings the first time this runs, and that backlog shouldn't silently start blocking every PR's merge the moment the scan is added. Triage the first report, then flip to `exit-code: 1` once it's clean or the remainder is consciously accepted — see the checklist.

## Token blacklist storage

`ROTATE_REFRESH_TOKENS=True` + `BLACKLIST_AFTER_ROTATION=True` means every refresh-token use writes an `OutstandingToken` and, after rotation, a `BlacklistedToken` row (`rest_framework_simplejwt.token_blacklist`). Nothing currently prunes expired rows — SimpleJWT ships a `python manage.py flushexpiredtokens` management command for exactly this, but it isn't wired into any scheduled job in this repo yet. This is an operational gap, not a security one on its own (unbounded table growth, not unbounded access), but left unaddressed long enough it becomes a real performance problem. See the [checklist](SECURITY_CHECKLIST.md) for scheduling it.

## Security monitoring

`core/security_events.py:log_security_event(event, request=None, **fields)` writes structured (dict-shaped) log lines to a dedicated `security` logger — for events worth a log aggregator or alerting rule watching in aggregate (a spike in failed logins, password-reset abuse, admin actions), as distinct from `AuditLog` (a permanent, queryable, per-object accountability record — see [User data isolation](#user-data-isolation)). Same rule as `AuditLog.metadata`: **never pass a password, JWT, refresh/reset/verification token, or raw request body into `log_security_event`'s fields** — this is permanent log storage outside the code's control once it leaves the process.

- **Centralized, not scattered**: `core.exceptions.security_aware_exception_handler` (wired as DRF's `EXCEPTION_HANDLER`) logs every `401`/`403`/`429` across the *entire* API automatically — a repeated-authorization-failure spike shows up in the logs regardless of which view it happened on, without every view needing to remember to log its own denial. Only `request.META`'s IP/user-agent and `request.path` are read automatically — never `request.data`, `request.body`, or the `Authorization`/`Cookie` headers.
- **Explicit business events** at the handful of points that aren't naturally an exception: `password_reset.requested`/`.completed`/`.invalid_token`, `google_login.success`/`.invalid_token`/`.nonce_mismatch`/`.unverified_email`, `session.logout_all`, and `admin.staff_status_change.success`/`.reauth_failed`.
- **The secret-free rule is enforced, not just documented**: `log_security_event` rejects (raises `ValueError`) any field whose name contains `password`/`token`/`refresh`/`secret`/`authorization`/`cookie` (case-insensitive substring match) — a call site that does something like `log_security_event('x', request=request, **request.data)`, or names a field `reset_token`/`current_password` by habit, fails loudly at the call site instead of quietly writing a credential to permanent log storage. Audited against every current call site when this was added; the one near-miss (a field originally named `linked_existing_password_account` in `GoogleLoginView`, which is about linking a *password-based account* to Google sign-in, not an actual password) was renamed rather than exempted, to keep the check a real guarantee instead of one with holes punched in it for convenience. Test: `core/tests.py:SecurityEventLoggingTests`.
- **Optional Sentry integration**: `config/settings.py` initializes `sentry_sdk` if `SENTRY_DSN` is set (unset in dev/CI — nothing is sent anywhere without it). `send_default_pii=False` and `traces_sample_rate=0.0` are explicit — errors only, no automatic request-body/cookie/email capture beyond what's deliberately logged elsewhere in this codebase.

## Reporting a vulnerability

If you find a security issue in this codebase, report it privately rather than opening a public issue — a public report gives an attacker a head start before a fix ships. Contact the maintainers directly with:

- What you found and where (file/endpoint).
- Steps to reproduce, or a proof of concept if you have one.
- What you think the impact is (what data/action it exposes).

Please don't test against the production deployment in ways that could affect real user data (e.g. don't attempt to actually exfiltrate another user's documents to prove the file-access issue exists — describe the gap in the check instead). Give a reasonable window to fix the issue before any public disclosure.
